# ミッション本体の設計・デバッグ指針

## `mission/`: ミッション制御の核

`mission/` は本番制御の核である。この層の役割は、センサー値を読むだけでも、モータを回すことだけでもない。ミッションを安全に進めるために、状態を理解し、判断し、異常時にも説明可能な形で終わらせることである。

### この層の完成条件

- フェーズ進行の理由が明確である
- センサー異常時の挙動が明確である
- 本番ログから判断過程を再構成できる
- 試験入口が増えても本番ロジックが壊れない

### 役割分担

- `const.py`
  - 調整可能な値の一元管理
- `st.py`
  - 共有状態の単一ソース
- `nav.py`, `gps_util.py`
  - できるだけ副作用の少ない計算・入出力補助
- `ctrl.py`
  - ミッション全体の司令塔
- `run.py`
  - 起動モードの整理
- `mgr/`
  - ハード制御・取得
- `phases/`
  - フェーズごとの意思決定

### 重要原則

- `ctrl.py` は「つなぐ場所」であり、「何でも書く場所」にしない。
- `CanSatState` は観測用の基盤であり、暗黙の副作用の置き場にしない。
- 本番ロジックにとって重要な判断は、ログから理由が追える状態にする。
- タイムアウトは単なる保険ではなく、ミッション戦略の一部として扱う。

### 何を改善していくべきか

- 判断理由の明示
  - フェーズ遷移、give up、goal 判定に理由文字列を持たせる。
- 観測点の整理
  - 「必要なログ」が事後に不足しないようにする。
- 状態の明確化
  - 共有状態は「現在値」「妥当性」「鮮度」の3要素で理解できるようにする。
- 変更容易性
  - フェーズ戦略や閾値変更が局所修正で済むように保つ。

### 実装上の指針

- 新しい制御戦略を入れるときは、どの層に属する処理かを先に決める。
- 一時的な実験用条件分岐は `runs/` 側に寄せ、本番層へ残さない。
- ログ列追加は `analysis/` の追従方針まで含めて設計する。
- 「とりあえず動く」コードより、「次の不具合を見つけやすい」コードを選ぶ。

### 主な観測対象

- `phase`
- `mission_end_reason`
- `phase7_arrival_reason`
- センサー freshness/stale
- 視覚検出の信頼度と理由
- モータ指令の種別と更新時刻

### 避けるべき状態

- 何が原因でフェーズが変わったか分からない
- センサー異常とセンサー未接続が区別できない
- 調整値が `const.py` 外へ散る
- 試験用コードが本番層の責務を侵食する

## `mission/mgr/`: 物理世界との境界

`mgr/` は「取れた値を返す」だけでなく、「今その値を信用してよいか」を上位が判断できるようにする。

### 目的

- ハード初期化の成否を明確にする
- 取得値の妥当性と鮮度を扱えるようにする
- モータ・LED などの出力系を安全側で制御する
- 異常時に再試行と諦め方の方針を持つ

### あるべき性質

- 初期化の透明性: 何回試し、なぜ失敗したかが分かる
- 入出力の安定性: 戻り値形式や意味がぶれない
- 回復可能性: 一時的不調に対し、再初期化や fallback を持てる
- 安全性: 出力系は常に停止を最優先する

### ファイル別の設計思想

- `hw_mgr.py`
  - 起動順序とデバイス準備を管理する
  - 起動時にどこで失敗したかが最短で分かるようにする
- `sns_mgr.py`
  - 観測データの正規化、鮮度管理、ログ化を担う
  - 値そのものと、値をどこまで信用できるかを分けて上位へ渡す
- `mtr_mgr.py`
  - 出力は必ず安全に変化させる
  - 急な反転や過大指令を避け、停止条件を優先する
- `led_mgr.py`
  - 状態表示のための I/O であり、現場オペレーションの一部として扱う

### 改善・デバッグ指針

- 取得失敗、値異常、値 stale を明確に区別する
- センサー再初期化の条件と上限を定数として説明可能にする
- 出力系のコマンドをログと対応づけやすくする
- ハード差分を吸収する調整値は局所化する
- 初期化の成否、リトライ回数、最終正常取得時刻、妥当値レンジ逸脱回数を確認する
- 再初期化後に回復したか、モータ停止が確実に通ったかを確認する

### 禁止事項

- 読み取り失敗を正常値のように見せること
- 出力制御で急停止・急反転の安全配慮を省くこと
- ライブラリ都合の例外を上位に無説明で漏らすこと

## `mission/phases/`: ミッションの意思決定

各フェーズが「何を達成したら次へ進むのか」「何を危険とみなして戻るのか」「いつ諦めるのか」を明文化する。

### 完成条件

- 入口条件、維持条件、脱出条件が区別されている
- フェーズ遷移の理由がログや出力から分かる
- 誤検知やセンサー欠落に対する保守動作がある

### 各フェーズに必ず持たせる視点

- 目的: そのフェーズで達成したいこと
- 成功条件: 何が観測されたら次へ進むか
- 失敗条件: 何が起きたら戻る、諦める、停止するか
- 観測根拠: 判断に使ったセンサーと信頼条件
- 時間戦略: なぜそのタイムアウトが必要か

### フェーズごとの設計思想

- `p0`: 降下・着地の誤判定を避けながら、遷移機会を逃しすぎない
- `p1`: 展開動作は安全優先で、再現性を損なう近道を入れない
- `p2`: キャリブレーションを以後の航法品質を左右する前提整備として扱う
- `p3`: 遠距離移動。方位ソースの信頼性を意識して保守的に判断する
- `p4`: 発見。誤検知を抑えつつ、探索不能状態を長引かせない
- `p5`: 接近。見失いと到達誤判定の両方を制御する
- `p6`: 最終突入。短時間・高確度・安全停止への接続を重視する
- `p7`: 終了状態。停止・通知・ログ確定を行う

### 改善・デバッグ指針

- 判断には、その場の値だけでなく連続性、鮮度、確認回数を使う
- 1つのフェーズが複数役割を持ちすぎたら分離を検討する
- 戻り遷移を成功率を上げる戦略として設計する
- timeout は次善策へ移るための戦略的判断として定義する
- 遷移した理由、遷移しなかった理由、信用したセンサー、fallback の動作を確認する

### 避けたい実装

- 閾値1本で全状況を説明しようとすること
- 入口時の一時状態リセットが曖昧なこと
- 遷移理由を説明できない phase update
